# Audit State Tool

`audit-state.cjs` builds and maintains every JSON file of a full-audit run. No agent writes JSON by hand. Agents write **record text** — `key: value` lines with no quoting or escaping — and the tool compiles it into the exact contracts in `report-schema.json`, `RECONNAISSANCE.md`, `HUNTING.md`, and `VALIDATION-AND-REPORTING.md`. The tool validates every write in-process with `validate-findings.cjs` and `validate-coverage-ledger.cjs`, writes atomically, and regenerates `progress.html` after every change.

The tool changes how files are produced, not what they contain. The ledger state table, verdict contracts, evidence bar, independence rules, and execution boundary are unchanged; the tool enforces them mechanically and reports violations by source line.

Invoke it as `node <skill-dir>/audit-state.cjs <command> --run <output-dir> ...`. `node <skill-dir>/audit-state.cjs help` lists every command. It needs only Node.js, like the validators.

## Ownership

- The parent is the only writer of shared run files. It changes them only through tool commands: never edit `run-metadata.json`, `coverage-ledger.json`, `findings.json`, `state/`, or `progress.html` directly.
- A delegated agent writes only its own `scratch/` directory (agents that run sandboxed checks) and its own result file `<output-dir>/agents/<agent-id>/result.txt`. The result file is never exposed to the sandbox or to target-controlled code.
- A delegated agent may run the read-only commands `check`, `template`, `brief`, `show`, and `status`. `template --write` writes only that agent's own result file.
- The parent never edits an agent's result file. When `ingest` rejects a result, send the reported lines back to the same agent to fix its own file if the platform can continue it; otherwise run `agent fail` and use a fresh agent. This keeps the existing rule that a malformed result is discarded rather than repaired by the parent.

## Run directory

```text
<output-dir>/
  run-metadata.json      parent, via init / metadata / finish
  architecture.md        parent, written directly (Markdown)
  coverage-ledger.json   parent, via units / agent / ingest commands
  findings.json          parent, via findings write (then kept in sync)
  progress.html          regenerated by every state-changing command
  REPORT.md, FINDINGS-DETAIL.md, NEEDS-VALIDATION.md   parent, Phase 6
  state/audit-state.json agents, candidates, proposals, phase, validator status
  state/events.jsonl     append-only activity log
  state/results/<id>.json  the compiled contract object of every ingested result
  agents/<id>/scratch/   sandbox-writable (hunters and verifiers only)
  agents/<id>/artifacts/ parent-promoted evidence (hunters and verifiers only)
  agents/<id>/result.txt the agent's record-text result, pre-filled with a template
```

The tool adds a parent `bookkeeping` object to each ledger unit, outside the semantic fields: a short alias (`U1`, `U2`, ...), priority rationale, hardening notes, validation decisions, carried fingerprints, resolved prior leads, and notes. Commands accept either the alias or the full `coverage_id`.

## Record text

```text
# comment
key: the value runs to the end of the line; never quote or escape it
key: <<<
several lines, kept exactly
(code, payloads, fixtures)
>>>
list_key: one item
list_key: another item
list_key:
- or items like this
[section]                 starts a new item: a unit, a check, a trace step, ...
key = null                exact JSON value, only when needed: null, "", "\u0000"
key:                      empty means "not provided"
```

- Dotted keys address nested objects: `severity.impact.score: medium`.
- Write an item's own fields before its sub-sections; a key that only an outer item defines still goes to that outer item.
- Sections nobody filled in are ignored, so templates can carry unused skeletons.
- `file: src/a.c:42` sets both `file` and `line` in trace and evidence entries.
- In a multi-step trace, `kind` may stay empty: the first step becomes `entrypoint`, the last `sink`, and the others `propagation`.
- If `<<<` ... `>>>` would be ambiguous because the text contains a line `>>>`, open with `<<<END` and close with a line `END`.
- A Markdown code fence around the whole file is ignored.

`node <skill-dir>/audit-state.cjs template <kind>` prints a commented template for `metadata`, `units`, `hunter`, `critic`, `verifier`, or `record-verifier`. Record templates are derived from `report-schema.json` at run time, including its field and verdict descriptions, so they cannot drift from the schema.

## Parent workflow

### Phase 1

```sh
node <skill-dir>/audit-state.cjs template metadata > <draft>.txt        # fill in
node <skill-dir>/audit-state.cjs init --run <output-dir> --file <draft>.txt
node <skill-dir>/audit-state.cjs agent start --run <output-dir> --agent recon-1a --role recon --note "Product, stack, local operation"
node <skill-dir>/audit-state.cjs agent finish --run <output-dir> --agent recon-1a
node <skill-dir>/audit-state.cjs units add --run <output-dir> --file <units>.txt
```

Keep drafts outside the target, for example in `<output-dir>/drafts/`. `init` refuses an output directory inside the target unless `--allow-inside-target` is passed after the version-control check in `SKILL.md`. It records `execution_policy`, the shared-file owners, and `run_status: "in_progress"` itself. `units add` derives each `coverage_id` from `canonical_refs` exactly as `RECONNAISSANCE.md` defines, assigns aliases, applies the defaults (`planned`, wave, empty evidence, `prior_status` `none` without prior runs and `new` with them), sorts, and rejects duplicate IDs and canonical identity collisions. Seed `deferred`, `out_of_scope`, or `not_applicable` units with `status` and an `unresolved` reason.

For a prior run, carry an unchanged record into a seeded `planned` unit whose `prior_status` is `prior_confirmed_same_source` or `prior_needs_validation`:

```sh
node <skill-dir>/audit-state.cjs carry --run <output-dir> --prior <prior-run>/findings.json --fingerprint <fp> --unit U5
```

`show units --run <prior-run>` and `show finding <fp> --run <prior-run>` read prior runs without changing them.

### Phase 2

```sh
node <skill-dir>/audit-state.cjs agent start --run <output-dir> --agent hunter-1 --role hunter --units U1,U2
node <skill-dir>/audit-state.cjs brief --run <output-dir> --agent hunter-1     # assignment material for the prompt
node <skill-dir>/audit-state.cjs ingest --run <output-dir> --agent hunter-1   # after the hunter replies
node <skill-dir>/audit-state.cjs agent start --run <output-dir> --agent critic-1 --role critic
node <skill-dir>/audit-state.cjs ingest --run <output-dir> --agent critic-1
```

`agent start` refuses a reused agent ID, a non-canonical ID, a unit that is not `planned`, and, when `budget` is set, any invocation past the strict budget. It sets the units `in_progress`, creates `scratch/`, `artifacts/`, and a pre-filled `result.txt`, and counts the invocation. `ingest` applies the per-unit contract in `HUNTING.md`: every assigned unit exactly once, owned checks, unit `reviewed_paths` equal to the union of check paths (computed when omitted), local artifacts that exist as regular files below the check owner's `artifacts/`, linked candidate fingerprints, and schema-valid candidates. A rejected result changes nothing except the agent's recorded errors.

Hunter `uncovered` entries and critic `missing_units` and `reassign_ids` become numbered proposals (`P1`, `P2`, ...). Resolve each:

- accept a unit: add it with `from_proposal: P3` in `units add` (use `status: deferred` with reason `quick_profile_final_critic` in a quick run);
- reassign: `units reassign --unit U3 --reason "<critic's source-backed reason>"` archives the live attempt and opens a fresh wave (`--defer <reason>` archives and defers instead);
- reject: `proposal reject --proposal P3 --reason "<why>"`.

Use `units status --units U4,U5 --to deferred --reason budget_cannot_reserve_critics_and_validation` for units the budget cannot reach, `agent fail --agent <id> --reason "<why>"` to release a failed agent's units, and `units note --unit U3 --text "<note>"` for bookkeeping notes. A final-clean critic uses `--role final-critic`.

### Phases 3 to 5

```sh
node <skill-dir>/audit-state.cjs agent start --run <output-dir> --agent verifier-1 --role verifier --fingerprint <fp>
node <skill-dir>/audit-state.cjs ingest --run <output-dir> --agent verifier-1
node <skill-dir>/audit-state.cjs findings write --run <output-dir>
node <skill-dir>/audit-state.cjs agent start --run <output-dir> --agent rv-1 --role record-verifier --fingerprint <fp>
node <skill-dir>/audit-state.cjs ingest --run <output-dir> --agent rv-1
```

Candidates are consolidated by fingerprint automatically. Consolidate different fingerprints with one root cause with `candidate duplicate --fingerprint <fp> --of <fp>`. Each verifier gets exactly one candidate and must be a fresh agent that never proposed, validated, or replaced it. The tool records each decision in every linked ledger unit. A carried prior record's verifier becomes the owner of its seeded unit, and its result must include a `[check]` for that unit.

`findings write` builds `findings.json` from the independently decided records, sorted by fingerprint, and validates it. After it exists, every later decision or applied replacement rewrites and revalidates it. Candidates without an independent decision are listed and never included.

A Phase 5 `replace` decision applies at once only when it changes no material field. The tool flags a stronger verdict and changes to the root cause, the trace beyond line numbers, execution input, observed result, impact, or severity. A flagged replacement waits for a fresh `record-verifier`, which reviews the pending replacement. If the flagged change is only wording or a line correction that changes no meaning or evidence, apply it with `record apply --fingerprint <fp> --non-material --reason "<why>"`. If no independent verifier is available, `record remove --fingerprint <fp> --reason "<exact reason>"` removes it from `findings.json` and the run must end incomplete. A record with a genuinely different root cause needs `--new-root-cause` on `ingest`; Phase 3 renames the candidate, and Phase 5 registers a new candidate for independent validation. In the `quick` profile the Phase 3 decision is final and the tool refuses record verifiers.

### Phase 6 and status

```sh
node <skill-dir>/audit-state.cjs status --run <output-dir>
node <skill-dir>/audit-state.cjs finish --run <output-dir> --status complete
node <skill-dir>/audit-state.cjs finish --run <output-dir> --status incomplete --reason validation_budget_exhausted
```

`finish --status complete` refuses while any unit is `planned` or `in_progress`, an agent is running, a proposal is open, a candidate lacks an independent decision or Phase 5 verification, a replacement is pending, a record was removed, or `findings.json` was never written. `status` prints counts, validator results, and next steps. `phase --set <n>` records the current phase when the commands have not already advanced it.

## Delegated agents

Every delegated prompt includes the output of `brief` for that agent. It contains the data parts of the prompt (assigned units and block maps, exclusions, peer-owned units, candidate or record under review, linked checks, paths, and the promotion allowlist when recorded with `--allowlist`, `--max-file-bytes`, and `--max-total-bytes`) and ends with these result-file instructions:

1. Your result file already holds a template for your role; fill it in as record text, never JSON.
2. Run `node <skill-dir>/audit-state.cjs check --run <output-dir> --agent <id>`.
3. Fix every reported line and run `check` again until it prints `OK`.
4. Reply with exactly one line: `RESULT agents/<id>/result.txt`.

An agent without a file-writing tool replies with the record text itself; the parent saves it unchanged as that agent's `result.txt` before `ingest`. A verifier that reaches a different decision regenerates a correctly shaped template with `template --run <output-dir> --agent <id> --decision <decision> --write --force`.

## Progress report

`progress.html` is a self-contained page, regenerated after every state change and with `report`. It shows the phase, coverage by status, candidates and their validation history, findings with full source traces and reproductions, agents and budget, open proposals and unresolved facts, hardening notes, `architecture.md`, and the activity log. Open it in a browser; while the run is in progress it refreshes itself every 15 seconds. All content is escaped, invisible and direction-changing characters are shown as `U+XXXX`, and a Content-Security-Policy pins the page's only script and style by hash, so text copied from the target cannot execute.
